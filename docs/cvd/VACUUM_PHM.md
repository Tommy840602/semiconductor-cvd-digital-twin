# 真空 PHM 操作與維護

首頁「真空 PHM」分頁顯示十台機台、三十組 LL 泵浦；製程頁的同名折疊區提供詳細曲線及受控回收。分數、剩餘抽氣次數與退化門檻都是 `synthetic-vacuum-v1` 示範值，不能用於實機壽命判斷。

## 正常監控

每個 LL 獨立累計抽氣。每次增加 0.001 退化，0.6 起預警；預警不中斷加工。達到 0.01 mbar 才可搬送，超過 12 個模擬秒即鎖住該 LL，整台停止新派片。壓力、健康曲線保留最近 30 天；達標率只含已成功／失敗週期，中斷另外顯示。過期資料顯示未知，不用舊分數宣稱目前健康。

## 故障與回收通道

1. Engineer／Leader 在故障 LL 按「受控排氣回收」。設備確認隔離、手臂與槽位後排氣，再回原 LP；未加工片保持未加工，已加工片保留結果。
2. 若 PM 尚有健康完成片卻沒有可用 LL，對已排氣、無片的故障 LL 按「修復並測試回收通道」。測試成功後可協助回收至各批原 LP，但正式新片仍暫停。
3. 申請整台保養，勾選本次泵浦。曾修復回收通道的泵浦必須納入；未修好的其他泵浦仍阻擋復機。
4. 排空後結束保養，啟動所選 LL 抽氣測試；同輪全數通過才能啟動既有四 PM Dummy。
5. Dummy 全部合格、回收並換回原 FOUP，且其他異常簽核已完成後，由 Engineer／Leader 按手動恢復加工。

Operator 只能查看。恢復模擬時鐘不等於恢復派片。收到 API 接受不等於設備完成，操作區會保留等待確認狀態。

## 失敗、中斷及重測

空腔抽氣測試期間重啟會保存中斷證據，保持故障與派片鎖，不將不完整測試判定合格。恢復測試時鐘後，在排空且無測試載具的狀態重新申請所需泵浦保養，再完整測試。需要時先卸下已回收的 Dummy 載具。新故障或再保養使原資格失效；配方變更沿用既有 Dummy 重驗規則。

## 部署與回退

部署前備份 PostgreSQL、十台 simulator checkpoint 與現有映像；先更新可讀新舊資料的後端和介面，再更新 simulator。既有無 PHM checkpoint 明確記錄新基準，舊活動抽氣完成後才用新模型，不補造過去資料。

回退前停止派片並保存最新 checkpoint。若存在 vacuumHold、故障、回收中、通道待保養或未完成測試，禁止直接以舊 simulator 覆蓋：舊程式不認識這些互鎖。應維持停用並先完成受控處置，資料庫歷史不刪除。可單獨回退前端／後端至備份映像而保留新 simulator 的安全鎖，但舊介面不提供 PHM 控制。

## 驗收

Go 測試覆蓋獨立退化、期限邊界、checkpoint、中斷、三泵故障回收與 Dummy 復機。`scripts/prepare-phm-validation.py` 建立獨立 Docker 專案；`scripts/verify-phm-stack.py` 僅對 localhost:19080 的隔離資料執行控制驗收，不可改成展示站位址。`tests/integration/vacuum_ui.cjs` 使用假資料驗證三語與手機介面。

驗收亦包含真實 API 的 Operator／CSRF 拒絕、MQTT 與 Kafka 重連、保養測試重啟中斷，以及四 PM Dummy 後人工復機。大量歷史訊息場景新增 `inbox_pending_delivery` 部分索引，避免每次派送查詢掃描所有已送出紀錄；不刪除歷史資料。

重連積壓時，`cvd.snapshot.v1` 以 Kafka 批次取出每台最高版本快照後更新畫面；`cvd.telemetry.v1`、故障與稽核事件仍逐筆處理。這只合併可取代的即時視圖，不改變一秒採樣歷史與統計。

十台共用 Docker 的展示設定使用 `CVD_GO_PROCS=1`（`GOMAXPROCS`），避免每個模擬器／閘道器都依整台主機核心數展開 GC 執行緒。可依部署硬體調整；不限制一秒採樣時鐘或改變設備互鎖。

重連時每個閘道器每輪最多回放 4 個待送事件，同一事件至少隔 30 秒才重送。設備與閘道器的耐久佇列仍保留至 Kafka 確認；此節流為十台同時回放保留快照與 ACK 的容量。

平台的最新快照使用單次 PostgreSQL 批次更新與 Redis pipeline；資料庫仍以版本條件拒絕舊快照。SECS/GEM 讀值與事件報告重用原始 JSON，避免反覆展開累積事件，並保持原始整數精度及線上格式。

Bridge 以有界的每機台佇列平行落盤，同一機台的 NBIRTH／DBIRTH／DDATA 順序保持不變；佇列滿時套用背壓，不丟棄事件。已用阻塞單機與跨機台順序測試、Go race 驗證。

`equipment_snapshot.body` 採用 PostgreSQL 16 的 LZ4 TOAST 壓縮，以降低高頻快照更新成本；歷史表保留原設定。首頁批次讀取十台快照，通訊狀態以同批每台最新 `sourceTime` 更新，避免過去未知／離線狀態長時間遮蔽已恢復的設備；較舊時間仍不得覆蓋較新狀態。
