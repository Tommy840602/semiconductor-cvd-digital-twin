## Context

參見 proposal.md。Go maintenance.go 目前在當輪四個 PM 製程判定通過並回槽後設 passed，載具還原設 ready；resume 只檢查設備測試及既有互鎖。Java MetrologyApi 以 process-result 和成功回 LP 的 movement-complete 配對建量測，已保存 purpose，但尚未把量測完成回饋保養復機。此變更跨設備模擬、後端、量測及 UI，因此需要設計文件。

## Goals / Non-Goals

**Goals:** 使保養復機以當輪量測與 PE 確認為必要條件，保留人員手動恢復及所有既有互鎖，持久保存證據。

**Non-Goals:** 不改一般生產片量測告警政策；不把本流程套入需要另位 Leader 的異常處置簽核；不擴增 OpenCV 簽核、真實 KLA 通訊或跨設備搬片。

## Decisions

### 證據與資格分開保存

沿用原設備製程判定與四片全部回槽的條件，另建量測資格資料，顯示等待 KLA、等待 PE、PE 退回或可手動恢復。不把原 passed 誤當完整復機資格。維持原換載具規則；換回 FOUP 不代替 PE 確認，量測工作由已持久化的當輪四片證據完成。相較全面重寫保養 phase，分開保存資格可保留既有排空、真空測試與載具交換邏輯。

### 量測綁定與判定

量測資格綁定 equipmentId、maintenanceId、generation、qualificationRunId、recipeVersion、四片 waferId／PM／processRunId 以及有效 metrology run/result version。沿用既有膜厚與均勻度模擬門檻並保存當輪快照，不另發明數值。必須檢查四片完整與來源有效，重新量測仍屬同一片，但結果替換使先前 PE 確認失效。量測終態通知採既有 Kafka 事件或持久資料的冪等消費，重複與亂序不得把舊結果覆蓋新結果。

### 確認與恢復

新增設備保養資格查詢、PE confirm/reject API，後端重新讀取當輪資格、目前帳號角色與 PE 部門，事務鎖定同一設備／保養週期，保存證據摘要及 digest。PE 可以確認後自己另按恢復；不新增雙人帳號分離。

後端 resume guard 必須確認當前證據 digest 等於有效 PE 確認，再送出含簽署資格識別的恢復命令。Go 驗證既有命令簽章、設備／週期／代次／輪次／配方及單次授權，並重查本地互鎖，不接受僅前端按鈕啟用的資格。PE 確認本身不送 resume。已排隊的恢復若遇新故障或代次變更必須拒絕。

### UI 與歷史

保養介面展示四個 PM 的加工、量測、門檻判定及 PE 確認，提供晶圓履歷連結。首頁／3D 沿用既有狀態摘要及多語言系統。PE Engineer／Leader 可確認、退回並填寫意見；其他角色只讀。Engineer／Leader 的恢復按钮只有所有互鎖成立時可用，並列出阻擋原因。

## Risks / Trade-offs

- [量測服務失聯或資料延迟] → 維持等待 KLA，不放行；服務恢復後冪等補處理。
- [確認與配方／故障變更競爭] → 後端事務鎖、證據版本與設備端代次檢查共同阻擋。
- [舊版本無資格欄位] → 能力版本未就緒時禁止新保養復機，不能預設已確認。
- [既有 Dummy 未能建立量測] → 遷移查核 processRunId 配對完整性；缺證據要求新輪，不生成假通過。

## Migration Plan

1. 增加資格、量測版本引用及確認事件資料結構，保留既有保養與量測資料。
2. 先部署後端與設備支援的能力版本，確認雙方就緒後啟用互鎖與 UI。
3. 已 released 週期保持歷史；尚未恢復週期皆要求四片有效 KLA 與 PE 確認。無法安全關聯的舊測試要求重新驗證。
4. 重啟復原與端到端測試通過後才展示可手動恢復。
5. 回退需保留新增證據與鎖定狀態，待驗證設備保持暫停；不得回退到允許舊 resume 繞過資格的組合。
