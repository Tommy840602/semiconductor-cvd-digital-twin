## Context

目前 Go 的 beginProcess 會建立空的膜厚與五點樣本，stepProcess 將目標膜厚除以當次沉積秒數計算速率。直接重用會清零，或令任意長度補做都再長一整個目標膜厚。configure 是全機配方且活動批次時拒絕；補做必須是獨立指令。Spring 目前只有 role，Redis session 固定保存登入身分，尚無部門與簽核狀態機。本變更涉及多服務、授權、數據模型與故障恢復，需要本設計。

## Goals / Non-Goals

**Goals:** 單片、單一核准版本、最多執行一次；保留已生長數值與原异常事實；互鎖等待不丟失核准意圖。

**Non-Goals:** 真實 TEL 製程校準、蝕刻或移除過厚膜層、任意步驟排序、亞秒級執行、搬回 LP 後重新上料補做、改寫全機 Recipe、自動恢復整批派片。第一版針對仍在 PM、保有製程數據的 exception 晶圓；正常已卸片結果不自動轉成此流程。

## Decisions

### 部門與角色

新增 department=EE／PE，獨立於角色。沿用角色繼承：EE 的 Engineer／Leader 可提案，PE 的 Engineer／Leader 可審核；Operator 不得提案或簽核，Leader 不因主管角色跨部門核准。提案人與審核人必須為不同帳號，即使中途調整部門也不可自審。

既有帳號及 cvd.leader 部門先標示未指定，保留既有讀取／日常權限與主管帳號管理能力，但不取得新流程權限。Leader 可在新增帳號時指定 EE／PE，並設定既有帳號部門；禁止改動既有角色或新增 Leader。部門調整留下稽核並使該帳號舊 session 失效，新登入才載入新部門；簽核歷史保存當時角色與部門，不被更改。

### 提案與版本

以 recoveryRequestId 與 revision 識別處方。保存 waferId、lotId、PM、來源 processRunId／異常處置版本、五點膜厚樣本及平均值、排錯原因與處理說明、目標膜厚、勾選步驟與秒數、模型／速率基準版本。基線數據由設備提供，EE 不可改寫當前膜厚。至少一個步驟，勾選步驟各 1–3600 整數秒，合計最多 3600；未勾選不執行，順序固定。

草稿可修改；送審後內容不可變。退回需說明；修訂另建版本。待執行核准版本若要修改，先原子撤銷執行意圖，再建立新版本重審。若指令已發布，須取得設備端未開始且取消成功的確認，才能宣告撤銷；若已開始則回覆狀態衝突，不得只取消資料庫紀錄。執行已開始則不可改秒數或撤回，只能沿用既有故障／停止機制。每片同時最多一個活動處置單，防止競爭補做。

### 簽核與自動執行

生命週期：draft → submitted → approved_waiting → executing → completed／failed；submitted 可 returned；送審／等待版本可 withdrawn／superseded；基線不符或已報廢則 invalidated。

PE 核准以單一 PostgreSQL 交易鎖定待審版本、寫審核紀錄及唯一的持久化執行意圖，不同步等待設備完成。發布工作器檢查設備：資料新鮮、同一 wafer／PM／來源狀態、仍為 exception、故障已解除、全域設備非暫停且通訊可用；批次派片暫停不是補做阻擋條件。條件不足保留 approved_waiting 與具體原因，條件滿足後自動發布。核准不自行解除故障或全域暫停。現有 resume 會因 exception 拒絕恢復，因此另提供已授權工程人員的「確認恢復補做時鐘」操作：僅在重啟檢查通過後解除設備時鐘暫停，保留 dispatchPaused 與批次暫停，不要求先結案異常片。此操作不產生補做核准，也不能代替 PE 簽核。

新 wafer-supplement 指令綁定核准版本、處方摘要與基線，不能由一般 /commands 接受使用者自帶 approvalId 直接注入。後端僅能由已核准執行意圖生成；設備端再次核對 wafer、PM、基線與已消費 executionId。臨時阻擋與永久基線失效分開回覆，不以重複產生新加工 ID 盲目重試。

每個執行意圖有固定 executionId。交易發布、網路重送、PE 重複點擊、設備 ACK 遺失或重啟均沿用同一 ID；設備在同一次持久化狀態更新保存「已開始」及數值，不得重複累積。逾時顯示結果待確認並查詢原 ID。審核、撤回、報廢與執行同時競爭以版本條件更新及設備最終核對決定唯一結果。

### 膜厚與步驟模型

新增 beginSupplement，複製既有五點樣本、膜厚、溫度等當前設備狀態，不呼叫清零 beginProcess。新增加工嘗試與 processRunId，並保留 sourceProcessRunId、recoveryRequestId、revision、executionId，凍結當次處方。

補做沿用原模擬製程的沉積速率基準（原目標膜厚／原沉積秒數）及既有氣體與噪聲模型，不能以補做秒數重新正規化到目標。因此補做沉積時間增加時，追加膜厚也隨之增加；目標膜厚用於核准比較與結果評估，不自動縮短核准時間。預熱、穩定化、吹掃維持膜厚，未選沉積時增量為零；僅選沉積時也不得因其他步驟為零而除零。

原模型的固定速率只是合成模擬，不承諾真實膜厚精度。UI 明示目前值、目標值、預估增量與最終實測模擬值。目標低於既有膜厚時不可聲稱補做可減薄；沒有去膜功能。

補做完成代表核准步驟執行完畢，不等於品質合格。沿用既有容差評估；不合格或再次故障保持 exception、保留新增膜厚，需新一輪 EE／PE 處置，不自動重試。合格片才走原 LL／原 LP 回收；整批仍暫停派片，保留既有人工恢復規則。

### 資料與畫面

PostgreSQL 新增處置單、不可變版本、審核事件及 outbox／執行意圖。查詢與審核 API 綁定 revision，409 表示版本／狀態衝突；無部門／角色權限 403。提交、退回、核准、撤回、發布、實際開始、完成／失敗分開記錄，不把核准等同執行成功。

Vue 提供 EE 異常晶圓提案表、PE 待審清單、前後／版本差異及核准確認頁，核准按鈕清楚標示會觸發執行。等待狀態即時更新原因。既有 PM 詳情及晶圓履歷串接完整時間線，批次 ID 仍按需顯示。

TimescaleDB 沿用每秒採樣與 30 天策略，補充前膜厚、累積膜厚、增量及步驟執行時間。PostgreSQL 活動處置與簽核鏈不得被普通歷史清理切斷；完成後至少與其可查詢製程歷史一併保留，過期清理整鏈處理。帳號變更不改寫簽核快照。

## Risks / Trade-offs

- [舊 rework 繞過簽核且清零] → 網站與後端拒絕舊入口，設備版本同步更新，保留舊歷史而不沿用舊命令執行新處置。
- [基線於審核期間變動] → 使用晶圓處置版本／五點基線，避開每秒都變化的整機 version；內容失效須重審。
- [等待核准後多次發送造成重複生長] → 固定 executionId、交易 outbox、設備持久化去重及重啟測試。
- [舊異常片缺少可還原樣本] → 顯示資料不足並阻止提交，不捏造零膜厚；保留原處置紀錄供人工處理。
- [簽核期間部門切換自審] → 歷史身分凍結、當次授權重新核對、禁止相同帳號核准。

## Migration Plan

1. 備份資料庫、模擬狀態與映像；新增部門及處置資料表，不猜測既有帳號部門。
2. 升級 checkpoint 與訊息契約，保留舊製程及五點樣本；一般加工與全機分步 Recipe 保持相容。
3. 隔離環境完成權限矩陣、補做前後膜厚、核准觸發、阻擋自動重試、重复核准／撤回競爭及斷線重啟驗證，再部署。
4. 部署時暫停新處置送出，完成版本切換後由 Leader 指派 EE／PE 帳號。既有帳號需重新登入載入部門。
5. 有待執行或加工中的補做不得直接降版到不理解簽核的模擬器；先排空或保留相容修復版本。回退不覆寫唯一 checkpoint 或刪除簽核歷史。
