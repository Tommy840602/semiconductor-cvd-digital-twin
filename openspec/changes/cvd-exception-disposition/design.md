## Context

參見 proposal.md。現有 RecoveryApi 提供不可變處方版本、EE／PE 授權及執行意圖；Go 在補做品質合格時立即標記成功並允許搬走。一般控制 API 的 scrap／resume／recovery-clock 僅檢查工程角色，尚無整台異常放行關卡。十台設備已使用完整 equipmentId 隔離，透過 SECS/GEM、Sparkplug B、Kafka 傳遞事件與指令。

本變更跨越資料庫、授權、設備持久化狀態及搬送排程，需要設計與遷移，不能只新增畫面按鈕。

## Goals / Non-Goals

**Goals:** 區分「執行完畢」「PE 確認」「已回收」「Leader 核准」「實際恢復」；保留既有膜厚、每台隔離與最多一次執行；任何旧指令不能跳過新增关卡。

**Non-Goals:** 真實製程合格認證、任意步驟排序、已回 LP 晶圓重新上料、代簽／交接制度、審核時限與自動升級、一般 recipe 改版簽核、跨機台放行。本版不新增尚未確認的簽核到期或代理政策；保留原提案人修訂規則，缺乏合格帳號時明示阻擋原因，不降低權限。

## Decisions

### 1. 異常紀錄與處置版本分離

以 dispositionId 對應不可變的來源異常，綁定 equipmentId、PM、waferId、lotId、sourceRunId、exceptionVersion、膜厚與五點樣本、設備及通訊狀態。設備先本地持久化異常與整台 dispatch hold，再發布事件；後端以事件身分去重建單，避免斷線期間照常派片或事件重播重複建單。

無晶圓的設備故障也納入機台阻擋集合，以設備排錯與結果確認結案，不製造虛構晶圓或執行補做。新建系統紀錄不視為 EE 簽名；由第一位有權限的 EE 提交排錯／方案後確立提案人。

EE 的原因、修復措施、驗證方式與結果獨立欄位，方案為 supplement 或 scrap。補做保持四步固定順序、整數秒、1–3600 秒總時間，基線只取設備；報廢需原因，不要求補做秒數。每次修訂另建版本並重新 PE 核准。用同一處置單保存多輪處置，避免退回或撤回被誤當作異常解除。送審與核准比對版本與來源基線，禁止換片、換機台沿用。

### 2. 三種狀態分開管理

處置決策：待 EE 排錯／草稿 → 待 PE 審核 → 已核准／等待設備 → 執行中。

執行與結果：
- 補做步驟結束 → 待 PE 結果確認（原 PM 留片）。PE 通過 → 待回收 → 已回原 LP → 處置完成待整台放行。
- 報廢核准 → 報廢標記與受控回收 → 已回原 LP、待 PE 結果確認 → 處置完成待整台放行。
- 補做不合格、再故障、PE 不通過 → 保存已生長膜厚與結果，回到待 EE 新方案，仍然阻擋派片。
- 報廢結果不符、搬送失敗或結果不明 → 保持阻擋並處理同一回收事件；不可把已報廢／已離開 PM 的晶圓當成可補做晶圓。

將 wafer 的 quality、disposition hold、return status 分開，不用 success 一個欄位同時控制品質、搬送與放行。補做品質不合格不得由 PE 按通過強制覆寫成合格；PE 可否決模擬合格結果並填原因。其他在途正常晶圓可以依既有安全機構完成及回收，但不得因任一處置完成恢復新派片。

### 3. PE 留片確認與回收授權

步驟結束時設備持久化待確認結果，不自動排入 PM 卸片。結果包含實際秒數、前／增量／後膜厚、均勻度、品質與執行 ID。PE 的 Engineer／Leader 可確認且不能是 EE 提案人；可與原 PE 審核人相同。確認綁定結果版本與 executionId，設備驗證晶圓仍在原 PM、結果未變，才消費唯一回收授權並搬回原 LL／LP 槽位。

PE 通過與回收到位不是同一狀態；回收失聯時顯示待確認，以原 ID 查詢，不能假定完成或再次回收。報廢始終保留 scrap 結果，確認回收不轉成 success。

### 4. 整台放行集合與不同人限制

設備維護持久化 dispositionEpoch／holdGeneration，每次新增阻擋異常或使原結果失效時遞增。放行快照包含 equipmentId、generation、所有未曾完成整台放行的處置 ID／最終版本／結果確認／回收證據及內容摘要，不使用每秒波動的整機 telemetry version。

Leader 必須屬 EE 或 PE，且帳號 ID 不得出現在本次集合中任何處置的 EE 提案、PE 審核或結果確認歷史，包括重提版本；變更部門不消除參與事實。已結束的前一放行週期不永久排除該人。所有人員資格由後端即時驗證，稽核保留當時身分。

僅當所有阻擋處置已確認並完成必要回收、沒有活動或未知處置執行、故障已解除、設備資料可信與互鎖滿足，才允許核准。資格或條件不足時列出具體阻擋項目。單一成功處置不能掩蓋同台其他 PM 異常。

### 5. Leader 核准到設備恢復

核准交易鎖定單台放行資料，產生固定 releaseId 與簽名執行意圖。發布經現有通道，設備在解除派片鎖的同一次持久化更新中核對 generation、處置集合、晶圓回收與互鎖；只有成功後才標記 released，後端收到設備證據後結案。

若只是傳輸失敗，查詢／重送同一 releaseId，不新增核准。若新增異常或集合／必要條件變更，拒絕且使舊核准失效，需重新具備條件並取得 Leader 核准。若新異常發生於原放行已完成之後，建立新 holdGeneration 並立即停止新派片；不能重播旧 releaseId 解鎖。

原子性以設備最終檢查為準，不能只用後端讀取快照後呼叫一般 resume，否則核准與新異常會競爭。每台獨立鎖與版本，不以全廠全域鎖串行化十台。

### 6. 防繞過與時鐘語義

舊一般 scrap 及清零 rework 拒絕。處置期內 resume、start、新批次派片、clear、recipe 更新、重啟恢復與 recovery-clock 皆不得清除 disposition hold。允許故障解除與設備時鐘恢復以完成已核准補做／回收，但絕不代表派片放行；UI 明示整台時鐘與派片鎖的區別。

不把所有人工維護暫停都冒充異常處置：没有異常放行週期時維持原日常控制契約。有異常週期時，一般 API 與设备兩層皆要求受核准的 releaseId 才能恢复派片。Leader 核准本身不自動清除硬體故障或跳過重啟檢查。

### 7. 資料鏈與畫面

擴充 PostgreSQL 處置、版本、排錯記錄、審核／結果確認、回收意圖與設備放行資料；保留舊 recovery ID、executionId 與不可變歷史。各種執行意圖採 transactional outbox、固定 ID 與設備 checkpoint 去重。異常鎖與待確認留片狀態必須在 Go 持久化，不能依賴 Redis 存活。

畫面分為「待 EE」「待 PE 審核」「執行／待確認」「待整台放行」，每張單清楚呈現處置類型、機台／PM／晶圓、等待原因與版本差異。機台詳情顯示阻擋數量及放行資格；Leader 確認頁展示完整集合與自動恢復的結果。退回、結果否決與撤回保留原因，設備執行 ACK 不替代人員確認紀錄。

業務與放行證據保存在 PostgreSQL，1Hz 曲線沿用 TimescaleDB；活動處置及其基線／結果證據不能被30天遙測清理切斷。新增欄位與指令需更新模擬 SECS/GEM profile、Sparkplug 指標、MQTT-Kafka bridge 與契約測試，不能假設 transport 自動相容未知動作。

## Risks / Trade-offs

- 原 PM 留片降低可用產能 → 清楚顯示待 PE 確認與占用原因，不在背景偷偷回收。
- 同台多單的參與人聯集使無人可放行 → 列出不符合資格原因與所需不同帳號，不預設同人代簽。
- 新異常與放行命令交錯 → 設備持久化 generation 與原子核對，訊息重播不能解除新鎖。
- 報廢不可逆且取消競爭 → 未開始才允許經設備確認撤回，已執行不得宣稱撤銷；保存取消／執行唯一結果。
- 舊活動版本缺少結果確認欄位 → 顯式遷移狀態並顯示待補確認，絕不偽造 PE 或 Leader 簽名。

## Migration Plan

1. 盤點並備份資料庫、十台 checkpoint、outbox、活動補做與在途晶圓；暫停新審核及派片，取得設備一致快照。
2. 新增資料結構與設備狀態版本，先部署能理解新 hold／結果／release 契約的消費端。逐一對照舊指令與尚未完成的執行意圖。
3. 舊草稿／送審單保留版本與身分，轉入完整處置並補齊排錯資料才可新送審；舊核准未執行方案缺少新版資料時轉為需修訂重審，撤銷原未執行意圖須取得設備確認。
4. 已開始補做沿用原核准版本與執行 ID，完成後進入 PE 留片確認；已完成且回 LP 的歷史不可搬回或捏造留片。若屬仍未放行的活動異常週期，保留已回收事實並補 PE 結果確認及 Leader 放行。真正已結束的舊歷史以 legacy 標示，不虛構新簽名。
5. 在隔離環境驗證補做與報廢全流程、異常集合競爭、斷線／重啟、舊入口拒絕及十台隔離，對帳後開放網站。
6. 新留片或放行意圖存在時禁止直接降版至會自動回收／resume 的舊模擬器；保留相容修復路徑。若部署尚未產生新業務事件，可完整還原一致備份；已有新事件時先保留與對帳，不能以舊資料覆蓋新稽核。
